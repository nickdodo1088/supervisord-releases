# 代码同步

> v0.9.8 起提供。退回 v0.9.7 及更早的版本前，先删除全部同步任务（从配置文件里删掉 `deploys`，再执行一次 `deploy approve`）：旧版本不认识 `deploys`，会拒绝加载整个配置文件。

## 要解决的问题

很多网站（PHP、HTML、前端编译结果）的上线方式是：代码推送到 Git 仓库，服务器上一个 root 脚本循环执行 `git pull`。这种做法有几个老问题：

- **账号密码隔一阵就要重新输入。** git 只把密码临时记在内存里（默认 15 分钟），或者令牌到期，脚本就卡住了。
- **失败了没人知道。** `git pull` 什么时候失败、为什么失败，只能去翻日志。
- **硬盘越占越多。** `.git` 保存每个版本的每个文件；把编译结果（如 `dist`）提交进仓库的项目，每发布一次就多一整份。
- **本地有改动就中断。** 线上文件被改过，`git pull` 会要求合并，然后停住。而生产环境本来就应该以仓库为准。
- **全程 root。** 脚本以 root 身份解析远端数据、改文件，出问题时影响整台机器。

supervisord 内置“代码同步”任务来替代这种脚本：在配置里写清楚仓库、分支、目录、文件属于哪个用户和组，之后推送代码就自动上线。

## 三个角色

```
                     Git 仓库（Gitee / GitHub / GitLab）
                              ▲
                              │ 用部署公钥拉代码（只读）
┌────────────── 服务器 ───────┼──────────────────────────────────────┐
│                             │                                      │
│  ① systemd（Linux 自带，本来就在运行）                                │
│     每 30 秒，或者在控制台点了“立即更新”                               │
│        │                                                           │
│        │ 以网站目录的属主（或配置里写的用户和组）启动，例如 ftpuser:www │
│        ▼                                                           │
│  ② 同步程序（运行几秒就退出，平时不占内存）                             │
│     · 问仓库：分支最新是哪个提交？没变就退出                            │
│     · 变了：只下载这一个提交 → 覆盖网站目录（权限照旧）→ 更新后命令     │
│     · 把结果写进状态文件                                              │
│     · 只能写这一个网站目录，其他目录一律写不了                          │
│        │                                                           │
│        ▼                                                           │
│     /srv/www/shop/api（文件属于 ftpuser:www）                         │
│                                                                    │
│  ③ supervisord 控制台（普通账号，没有任何特权）                         │
│     · 读状态文件：当前版本、上次检查时间、是否失败、更新记录              │
│     · 显示部署公钥，方便复制                                           │
│     · 点“立即更新 / 暂停 / 回滚”时，让 ① 马上启动 ②                     │
└────────────────────────────────────────────────────────────────────┘
```

- **① systemd** 做需要 root 的那件事：以网站用户的身份启动同步程序。它是系统自带的，supervisord 不需要另写任何 root 程序。
- **② 同步程序** 做真正的活，相当于原来的脚本。它就是 supervisord 程序本身的另一种运行方式（`supervisord deploy run 任务名`），不用另装。这个命令由 systemd 自动执行，你永远不需要手动执行它。
- **③ supervisord** 只负责看和点，不碰网站文件。

## 推送代码后发生了什么

全自动，没人需要动：

1. 开发者 `git push`。
2. 30 秒内，systemd 以网站目录的属主（例如 ftpuser:www）启动同步程序。
3. 同步程序用部署公钥问仓库：分支最新的提交是哪个？和网站上的一样就退出，整个过程几十毫秒。
4. 不一样：只下载这一个提交，然后：
   - 网站目录里的文件改成和仓库完全一致：线上被改过的文件覆盖回仓库版本，仓库删掉的文件也删掉（前端每次编译后文件名会变的 js、css、图片，上一版的会删掉，不会越积越多）；
   - [白名单](#白名单)里的文件不动，其余仓库里没有的文件和目录全部删除；
   - 写出的文件保持网站原来的权限（见“[权限](#权限)”），执行更新后命令；配置了[更新后通知](#更新后通知)的，再通知主机面板（例如清 PHP 的 OPcache、APCu、Yac 缓存）。
5. 结果写进状态文件。控制台显示“已更新到 abc1234（提交说明，作者，1 分钟前）”。

一天推送 100 次，就自动更新 100 次。

远端没有新提交时，每次检查也会核对网站目录：仓库里的文件被改动或删除，或者多出了白名单以外的文件（例如被上传的木马），会马上恢复成仓库版本，并执行更新后命令、发出更新后通知（清掉 OPcache，已删除的脚本就不会再从缓存里执行）。恢复和删除了哪些文件会显示在任务卡片和更新记录里，概览页的动态也会提示。

## 新增一个网站

最简单的做法：在控制台“代码同步”页面点“新增同步任务”。向导分五步，每一步都写明做什么、为什么，命令都可以直接复制：开始之前（停掉原来的脚本、装好 git）、网站文件归谁（默认用网站目录现在的属主）、仓库和目录、保留哪些文件、保存并批准（备份、保存、批准，以及批准时每个问题怎么回答）。任务出现在页面上以后，卡片会一直显示设置进度和下一步要做的事，直到第一次同步成功。

手动配置也是下面几步，一次性做完，以后不用再管。

**0. 网站文件归谁：**

面板建的网站什么都不用做：任务里不写 `user` 和 `group`，批准时读出网站目录现在的属主和组（面板给这个网站建的账号，常见的是 FTP 账号），同步程序就以它运行。写出的文件和面板建的属于同一个账号，FTP、SFTP 照样能改网站。

没有面板，或者网站目录还没建、属于 root 的，在任务里写上 `user` 和 `group`。没有合适的账号可以新建一个：

```bash
sudo useradd --system --shell /usr/sbin/nologin webdeploy
```

这个账号的密码是锁住的，登录程序是 `nologin`：SSH 登录不了，用 `su` 也切换不过去，同步程序由 systemd 直接用它启动，用不到密码。它也不用加进网站进程的组：文件属于哪个组由任务里的 `group` 决定。想让网站进程改不了代码，就用这样一个单独的账号做 `user`，`group` 写 nginx 的组。

第一次同步前最好先备份网站目录，例如 `sudo tar -czf /root/backup-site.tar.gz -C /srv/www site`：保留名单漏写的文件可以从备份里找回。

**1. 在 `supervisord.yaml` 里写任务：**

```yaml
deploys:
  shop-api:                 # 面板建的网站：文件属于网站目录现在的属主
    repo: git@git.example.com:shop/api.git
    branch: master
    directory: /srv/www/shop/api
    keep: [runtime/, .env]
    writable: [runtime/]
    after: /usr/bin/php /srv/www/shop/api/think clear

  shop-admin:               # 指定账号
    repo: git@git.example.com:shop/admin.git
    branch: publish
    directory: /srv/www/shop/admin
    user: webdeploy
    group: www
    keep: [dist/config/]
```

**2. root 批准一次：**

```bash
sudo /opt/supervisord/bin/supervisord deploy approve
```

它逐个列出任务的仓库、目录、用户和组（没写时是网站目录现在的属主和组）、保留目录和更新后命令，确认后输入 `y`。在终端里运行 `install.sh` 时，如果有待批准的任务，它也会顺便问。

批准后任务马上开始运行，**不需要在控制台点“重新加载配置”**：任务由 systemd 运行，控制台自己会显示批准过的任务。就算点了“重新加载配置”，也只会重启配置有变化的程序；新增、修改、删除同步任务都不会重启任何程序，也不会挡住热升级。

也可以不手写：在控制台“代码同步”页面点“新增同步任务”，填好后点“生成配置”。它按同样的规则检查填写的内容，给出要复制到配置文件的文字（YAML 或 INI，按你的配置文件格式）和批准命令；控制台只生成文字，不改服务器上的任何东西。

**3. 添加部署公钥：** 打开控制台的“代码同步”页面，复制这个任务的部署公钥，粘贴到仓库设置里：

- Gitee：仓库 →“管理”→“部署公钥管理”→“添加部署公钥”
- GitHub：仓库 → Settings → Deploy keys → Add deploy key（不要勾选写权限）
- GitLab：仓库 → Settings → Repository → Deploy keys

不需要在服务器上登录 git，也不需要先手动 `git pull` 一次。第一次同步由同步程序自己完成：目录里已经有代码的，直接按仓库覆盖。

## 什么时候需要 root 登录服务器

只有新增或修改同步任务的时候：在 `supervisord.yaml` 里加或改任务，然后执行一次 `deploy approve`。之后推送代码、检查、更新、调权限、清缓存全都自动完成，不需要任何人登录服务器或执行命令。

| 操作 | 要不要批准 |
| --- | --- |
| 推送代码（不管一天多少次） | 不要，全自动 |
| 控制台点“立即更新”“暂停”“恢复”“回滚” | 不要 |
| 新增一个同步任务 | 要，一次 |
| 修改任务的仓库、分支、目录、用户、组、保留目录、可写目录、更新后命令、更新后通知或检查间隔 | 要，一次；批准后下一次检查就按新的设置整理网站目录（可写目录、保留名单），不用等新的提交 |
| 没写 `user` 和 `group` 的任务，网站目录换了属主（例如面板换了网站的账号） | 要，一次；在那之前同步不更新，`deploy approve` 会列出“网站目录的属主变了” |
| 删除任务 | 批准时确认删除；批准前任务会先暂停 |

**不用记命令：** 有任务等待批准时，控制台的“代码同步”页面和概览页会醒目地提示“有 N 个任务等待批准”，并给出要执行的命令和“复制”按钮；在终端运行 `install.sh` 时也会主动询问。批准只能在服务器上以 root 完成，控制台不能批准，原因见下面。

**为什么要批准：** `supervisord.yaml` 这个文件 supervisord 自己能改。万一 supervisord 被攻破，攻击者就能改配置，让同步程序以网站用户的身份去写别的目录，或者执行别的命令。批准由 root 确认，确认后的内容另存一份 supervisord 改不了的副本（`/opt/supervisord/deploy/任务名/spec.json`，属于 root），systemd 和同步程序只认这一份。配置改了但还没批准时，任务照旧按上次批准的内容运行，控制台提示“配置有改动，等待批准”。

批准时还会拦下这些：

- 网站用户或组属于 root、supervisord 或 sudo、wheel、adm、shadow、docker、disk 等特权组。同步程序在每次启动时核对账号实际得到的主组和附加组；
- 没写 `user` 和 `group`，网站目录却还不存在、属于 root，或者组是 root：这时要在任务里写上它们；
- 目录是系统目录（`/etc`、`/usr`、`/var/lib` 等）、软件包的目录，或者 `/opt/supervisord` 本身；
- 网站目录是符号链接，或它的任一上级目录是链接、不属于 root、或者 root 以外的账号能写（例如 `/srv/www` 属于网站用户）。否则上级目录的所有者可以在批准后把网站目录换到别处，让同步以网站的组写入别的目录。网站目录本身可以属于网站用户。批准时会给出修改命令，例如 `chown root:root /srv/www && chmod go-w /srv/www`；同步程序每次运行前也会重新检查；
- 仓库地址只接受 HTTPS 和 SSH（`git@主机:路径`、`ssh://`）。HTTPS 地址中的用户信息和 SSH 地址中的密码会被拒绝，因为仓库地址会显示在控制台。私有仓库可以使用任务的 SSH 部署密钥。

更新后通知（`notify`）不是 Unix socket 时也不能批准；还不存在（提供它的服务没运行）或者不属于 root 时只提醒。

写了 `user`、网站目录却属于别的账号时（例如原来的脚本以 root 身份建的），同步程序可能写不了。批准时会说明，并单独询问是否一次性把整个目录改成 `用户:组`，`--yes` 不能代替这个确认。递归修改所有者会跳过嵌套挂载点，遇到需要改所有者的多重硬链接文件会报错。被锁定为不可修改的文件（`chattr +i` 或 `+a`，例如面板放的 `.user.ini`）会单独列出，所有者不变。

谁能改网站文件，批准时不检查：网站进程、FTP 账号是不是以同一个账号运行，由面板或者你自己决定。

更换网站用户的 UID 后，同步程序会生成新部署密钥并重建缓存和回滚记录。旧账号的数据保存在任务目录下只有 root 可进入的 `.previous-*` 目录中。请在仓库端撤销旧公钥，并添加控制台显示的新公钥。

## 配置项

| 配置项 | 必填 | 说明 |
| --- | --- | --- |
| `repo` | 是 | 仓库地址：`git@主机:路径`、`ssh://…` 或 `https://…`（公开仓库） |
| `branch` | 否 | 分支，默认是仓库的默认分支 |
| `directory` | 是 | 网站目录，绝对路径 |
| `user`、`group` | 否 | 网站文件的用户和组，同步程序以这个身份运行。两个都不写：用网站目录现在的属主和组（面板建的网站这样写）；要写就两个一起写 |
| `keep` | 否 | 白名单：相对于网站目录、同步不删除的目录和文件，例如 `[runtime/, .env, dist/config/]`。只对仓库里没有的文件有效：仓库里有的文件总是以仓库为准 |
| `writable` | 否 | 组可写的目录，例如 PHP 要写的 `runtime/`；不存在会自动创建，也算在白名单里 |
| `after` | 否 | 每次更新后执行的命令，以 `user:group` 身份在网站目录里运行，2 分钟超时。不经过 shell；要用管道等写法时写成 `/bin/sh -c '…'` |
| `notify` | 否 | 主机面板提供的 Unix socket 的路径，例如用来清 PHP 缓存；见“[更新后通知](#更新后通知)” |
| `interval` | 否 | 检查间隔，默认 `30s`，最短 `10s` |

v0.9.12、v0.9.13 的 `sftp_user`、`sftp_readonly` 已经不起作用，见“[SFTP、FTP 改文件](#sftpftp-改文件)”；留在配置里照样能加载，任务也不用重新批准。删掉它们算改了任务，要批准一次，账号和部署公钥都不变。

## 白名单

网站目录里只能有两种文件：仓库里的文件和白名单里的文件。白名单包括：

- `keep` 列出的目录和文件，例如前端的 `dist/config/`、PHP 的 `.env`；
- `writable` 里的可写目录：网站进程在里面写数据，例如缓存和上传的文件；
- 仓库的 `.gitignore` 忽略的文件；
- 被锁定为不可修改的文件和目录（`chattr +i` 或 `+a`，只有 root 能锁），例如面板放的 `.user.ini`：谁都删不掉，同步也不删，不用写进 `keep`。

其他文件和目录，不管是谁放的，每次检查都会删除，包括嵌套的 Git 仓库（普通的 `git clean -fd` 会跳过它们，在目录里 `git init` 就能把木马藏起来）。白名单里的文件同步一律不动；但仓库里也有的文件以仓库为准，`keep` 保不住，控制台会提示。

- **白名单写得越小越好。** 能写文件就不要写整个目录，例如写 `dist/config/config.js`，而不是 `dist/config/`。白名单目录里新出现的文件也不会被删除。
- **原来的保留规则要一起搬过来。** 原来脚本里 `git clean -e` 排除的路径，和网站目录里 `.git/info/exclude` 写的规则，同步都不会读，要写进 `keep`。第一次同步删除了哪些文件，会显示在任务卡片上。
- **挂载进网站目录的目录**（例如 NFS 上的上传目录）一定要在白名单里。
- **更新后命令生成的文件**（例如在服务器上编译出来的文件）不在白名单里也可以：两次更新之间的检查不会删除它们，每次更新时先删除，再由更新后命令重新生成。检查时只放过更新后命令留下的那些文件，之后再多出来的文件照样删除。
- **Vue 等项目会把 `public/` 原样复制进 `dist/`。** 如果 `public/config/` 里有文件，发布分支里就有 `dist/config/`，它总是以仓库为准；服务器上自己的配置不要放在仓库里也有的路径下。

## 权限

同步程序只管自己写出的文件，保证网站照常能读，别的文件和目录一概不动：谁能改网站，由面板（或者你自己）决定。

- **替换的文件**（更新、恢复、回滚时重写的仓库文件）保持原来那个文件的权限位、ACL 和组。仓库里标成可执行的文件，能读它的账号也能执行。Git 清空一个目录时会删掉它再重建（例如前端每次编译换掉 `assets/` 里的全部文件），重建的目录同样保持原来的权限位、ACL、默认 ACL 和组。
- **新文件和新目录**照所在的目录：目录有默认 ACL（面板建的网站一般都有）就按默认 ACL；没有的话，能进这个目录的账号和组都能读新文件、进新目录，只有属主能写。例如目录是 `0755`，新文件是 `0644`；目录是 `0750`，新文件是 `0640`；目录的 ACL 给了 PHP 的账号 `r-x`，新文件给它 `r--`。
- **`writable` 里的目录**，和里面属于 `user` 的文件，组可写；带 ACL 的，原来能读的账号也都能写。其他人的权限不变。
- **更新后命令**写出的文件按 umask `0022`：能进目录的人都能读。
- 新文件属于 `user`。目录有 setgid 位时，新文件和新目录属于目录的组，新目录也带 setgid；同步程序的 systemd 单元不允许设置 setgid（`RestrictSUIDSGID=`），所以它通过 ACL 改这些目录的权限，不用 `chmod`，setgid 位保留。
- 每次调整权限后，同步刷新 Git 的索引。否则改权限变了文件的 ctime，下一次更新时 Git 会把这些文件当成改过，删掉重写一遍。

## 面板建的网站

主机面板建的网站常见这样的设置：网站目录属于面板的 FTP 账号，组是 nginx 的组，目录带 setgid 和 ACL；每个网站的 PHP 用单独的账号，靠 ACL 读文件；运行目录里有面板锁定的 `.user.ini`。同步可以直接用在这样的网站上：

- 任务里不写 `user` 和 `group`。同步以网站目录的属主和组运行，写出的文件和面板建的一样：PHP 照样靠 ACL 读，nginx 照样靠组读，FTP 账号照样能改。
- 面板放进网站目录的默认文件（`index.html`、`404.html` 等）仓库里没有的话，第一次同步会删除，要保留就写进 `keep`。面板在网站目录里验证证书的话，把 `.well-known/` 写进 `keep`。
- 仓库里不要放面板会锁定的文件（例如运行目录里的 `.user.ini`）：同步改不了被锁定的文件，更新会失败。
- PHP 的 `opcache.revalidate_freq` 如果设得很大（有的面板是 3600 秒），更新后要过这么久才会用新代码。网站自己的脚本通常不能清 OPcache（面板用 `opcache.restrict_api` 禁止），`after` 也就帮不上。面板能在更新后清除缓存的，配置[更新后通知](#更新后通知)；否则在面板的 PHP 设置里把它改成 2 秒左右。
- 面板照常管理网站目录的权限（例如“修复权限”），同步不会改回去；之后替换文件时沿用面板设的权限。面板换了网站目录的属主（例如换了 FTP 账号），同步先停下不更新，任务卡片上提示执行一次 `deploy approve`，批准后改用新的账号。

## SFTP、FTP 改文件

谁能改网站文件由面板决定，同步不管：面板的 SFTP、FTP 账号照样能改。但同步每次检查都让目录和仓库保持一致：

- **用 SFTP 改过的仓库文件**，下一次检查（默认 30 秒内）改回仓库的版本；新加的文件不在白名单里就删除。控制台会记下改回和删除了哪些文件。
- **长期用 SFTP 维护的文件**，例如上传的图片、服务器上的配置，写进 `keep` 或 `writable`。
- **临时用 SFTP 改代码排查问题：** 先在控制台点“暂停”，暂停期间同步不检查、不改回；改好后把改动提交到仓库，再点“恢复”。没提交的改动恢复后会被改回去。
- **SFTP 新建的目录**属于 SFTP 登录的账号。任务以别的账号运行、又删不掉它的时候，检查会失败并写明是哪个目录：用 SFTP 删掉它，或者写进 `keep`。任务以网站目录的属主运行时没有这个问题。

**从 v0.9.12、v0.9.13 升级：** `sftp_user`、`sftp_readonly` 不再起作用，可以从配置里删掉（删掉后批准一次），留着也没关系。以前按它们设过的 ACL 不会自动改回：设成只读时去掉的写权限，要让 SFTP 账号重新能写，用面板的“修复权限”。以前批准时把整个目录改成了单独账号（例如 `webdeploy`）的，想改回面板的账号：用面板修复一次网站的所有者和权限，再从任务里删掉 `user` 和 `group`，执行一次 `deploy approve`。任务换了账号会生成新的部署公钥：在控制台复制新公钥，加到仓库的部署公钥里。

## 更新后通知

主机面板这类服务可以在网站更新后做同步做不了的事，例如清除 PHP 的 OPcache、APCu、Yac 缓存（同步以网站用户运行，没有权限重载 php-fpm）。面板提供一个 Unix socket，在任务里写上它的路径：

```yaml
    notify: /run/panel/php-cache.sock
```

同步每次改动了网站目录，都在更新后命令之后连接这个 socket，告诉它改了什么：更新到新提交、恢复被改动的文件、按新批准的设置整理目录、回滚。面板的回复会记在任务的更新记录里；没有回复、连不上或者面板报错，只记一条警告，网站照样是新版本。面板没收到的通知（没在运行、没有回复，或者回复说忙），同步在之后每次检查时重发，直到送达，期间的改动合并进同一条通知；送达后警告消失。面板回复失败的（`ok` 为 `false`）不重发：它可能已经做了一部分，例如清了几个网站共用的缓存。

socket 要放在 `/run` 这类目录里：同步程序的 `/tmp`、`/var/tmp` 和 `/dev` 是自己私有的，那里的 socket 连不上，配置会被拒绝。

**协议（第 1 版）。** 每次通知新建一个连接，同步写一行 JSON（以换行结尾），面板回一行 JSON。整个过程最多 30 秒。

```json
{"version":1,"task":"site","directory":"/srv/www/site","action":"update","from":"<原来的提交>","to":"<现在的提交>","changed":["app/controller/Index.php","public/index.php"]}
```

- `action`：`update`（新提交）、`restore`（恢复被改动或多出来的文件）、`apply`（按新批准的设置整理目录）或 `rollback`（回滚）。
- `from`、`to`：完整的提交号。第一次同步时 `from` 为空。
- `changed`：内容有变化的路径，相对于 `directory`，包括删掉的文件；整个删掉的目录以 `/` 结尾。不知道改了哪些时为 `null`（第一次同步、超过 10000 个，或者整条消息会超过 1 MiB）；只调整了权限时为 `[]`。
- 回复：成功时 `{"ok":true,"message":"…"}`，失败时 `{"ok":false,"error":"…"}`；什么都没做、要同步稍后再发时（例如忙）加上 `"retry":true`。`message` 和 `error` 会去掉控制字符、截到 300 字节后显示在控制台。
- 重发的通知合并了期间的改动：`from` 是面板最后收到的那次之后的提交，`changed` 是这些改动的并集（有一次不知道就是 `null`），`action` 是最近一次的。

**面板要检查的。** 任何本机账号都能连上 socket，面板要自己确认请求来自哪个任务：

- 用 `SO_PEERCRED` 取连接方的 UID，读请求里 `task` 对应的批准文件，要求 UID 是 0 或者是批准文件里 `user` 的 UID，`directory` 和批准文件里的一致（按真实路径比较）。
- 先检查任务名：`^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`。
- 请求最多 1 MiB；`changed` 里的路径只能在 `directory` 里面，不能有 `..`、绝对路径或 NUL。
- 同一个网站的通知按顺序处理，并限制频率。

**批准文件。** `/opt/supervisord/deploy/任务名/spec.json` 是 root 批准过的任务内容，只由 `deploy approve` 以 root 写入（属于 root，权限 `0644`），删除任务时连同目录一起删掉。面板可以读它，认出哪些目录由同步管理。读之前先确认它属于 root、组和其他人不可写，不跟随链接。里面的字段名保持不变，没设置的项可能不出现：

```json
{"name":"site","repo":"git@git.example.com:shop/site.git","branch":"main","directory":"/srv/www/site","user":"ftpuser","group":"www","keep":["config/"],"writable":["runtime/"],"after":"","notify":"/run/panel/php-cache.sock","interval":30,"from_directory":true,"digest":"…","approved_at":"…"}
```

- `user`、`group` 总是同步程序实际运行的账号和组。任务里没写时，是批准时网站目录的属主和组，这时 `from_directory` 为 `true`。
- v0.9.13 及更早批准的任务可能还有 `sftp_user`、`sftp_readonly`，它们已经不起作用，忽略即可。

面板可以照常管理这些目录（`directory` 及其下面）的权限，同步不会改回去：它只给自己写出的文件设置权限，照被替换的文件或所在的目录（见“[权限](#权限)”）。面板换了网站目录的属主后，`from_directory` 的任务要重新批准一次；在那之前同步不再更新网站，免得写出属于旧账号的文件，任务卡片上会写明要执行的命令。

## 硬盘空间

- **网站目录里没有 `.git`。** Git 数据放在 `/opt/supervisord/deploy/任务名/work` 下，也就不存在 `.git` 被网站访问泄露的风险。网站目录里原来的 `.git` 不会被动，控制台会显示它占了多少空间，确认后可以自己删掉。
- **只下载最新的一个提交。** 不下载历史。
- **只保留最近 5 个版本用来回滚，其余每次更新后立即删除。** Git 占的空间大约是代码压缩后的几份，不随更新次数增长。实测：一个每次提交都替换 200 KB 编译文件的仓库，连续更新 30 次后，同步缓存是 772 KB，同一仓库带完整历史是 7.2 MB；更新次数越多，差距越大。
- 控制台显示每个任务占用的空间。

## 命令行

| 命令 | 用途 |
| --- | --- |
| `sudo /opt/supervisord/bin/supervisord deploy approve` | 批准新增或修改的任务，删除配置里已经没有的任务（root） |
| `sudo /opt/supervisord/bin/supervisord deploy approve --list` | 只列出等待批准的任务 |
| `sudo /opt/supervisord/bin/supervisord deploy status` | 查看每个任务的批准状态、当前版本和上次检查 |
| `journalctl -u 'go-supervisord-deploy@*'` | 同步程序的运行记录 |

`deploy run 任务名` 是 systemd 调用的同步程序，不需要手动执行；以 root 执行会被拒绝。

## 控制台

“代码同步”页面每个任务显示：

- 状态：正常、更新中、失败、已暂停、等待批准；
- 仓库、分支、网站目录、文件的用户和组（任务里没写时，是批准时网站目录的属主和组）；
- 当前版本：提交号、提交说明、作者、时间；
- 上次检查时间；失败时的原因和连续失败次数；
- 最近的更新记录：时间、从哪个版本到哪个版本、用时、结果；恢复时列出恢复和删除了哪些文件；配置了更新后通知的，还有面板的回复。

按钮：

- **立即更新：** 不等 30 秒，马上检查并更新。
- **暂停、恢复：** 暂停期间不自动更新。
- **回滚：** 退回最近 5 个版本中的任意一个。回滚后自动更新会暂停，避免下一次检查又更新回去；点“恢复”继续。
- **部署公钥：** 复制公钥，并说明粘贴到哪里。

失败时会退避重试，间隔逐步拉长，最长 10 分钟一次，避免仓库或网络出问题时频繁请求。概览页显示有几个任务失败。

## 安全设计

- **supervisord 没有任何特权。** 它只读状态、显示公钥、传递“立即更新、暂停、恢复、回滚”请求。跨账号交换数据使用有大小上限的普通文件，控制台解析并显示 Ed25519 公钥。回滚只接受已批准任务保留的完整提交标识。
- **同步程序以网站用户运行，并且有 systemd 沙箱：**
  - 除了网站目录和它自己的数据目录，整个文件系统只读；
  - 没有任何 Linux 能力（capabilities），不能提权；
  - `/tmp` 私有，只允许 Unix、IPv4 和 IPv6 网络。

  任务仍可以使用网络，并读取沙箱允许且网站账号有权读取的文件。需要让两个网站互相隔离时，分别使用专用的网站账号。
- **同步不改谁能改网站：** 网站进程、FTP 账号能改哪些文件，由面板（或者你自己）设置，同步只保证自己写出的文件权限照旧。同步保证的是代码只来自仓库：每次检查都恢复被改动的仓库文件、删除白名单以外的文件，并在控制台留下记录。想让网站进程连一时也改不了代码，就让文件属于网站进程以外的账号：任务里写 `user`（例如 `webdeploy`），`group` 写 nginx 的组。
- **可写目录不要执行脚本：** 通过网站漏洞上传的木马，落在白名单以外的下一次检查就会删除；可写目录在白名单里，同步不会删除。在 nginx 里禁止这些目录执行 PHP，例如在处理 `.php` 的 `location` 之前加上 `location ~ ^/(runtime|uploads)/.*\.php$ { deny all; }`。
- **同步防不住拿到网站账号的人：** 同步程序以网站账号运行，有这个账号的人（例如 SFTP 密码泄露）也能改网站和同步程序自己的数据。同步能做到的是：每次检查都恢复代码、删除多出来的文件，并在控制台留下记录。
- **root 的部分只由 systemd 按 root 批准过的配置执行。** 没有常驻的 root 程序，没有 socket，也没有 RPC，所以也不存在“谁能连上来”的问题。更新后通知是同步程序主动连面板的 socket，只发出改了什么，不接受任何命令；面板那一端要做的检查见“[更新后通知](#更新后通知)”。
- **部署公钥：** 每个任务一把，只对这一个仓库有效。私钥只有网站用户能读；控制台只显示公钥。
- **Git 加固：**
  - 不执行仓库里的钩子，不拉子模块；
  - 校验下载的每个对象；
  - 只允许 HTTPS 和 SSH；
  - 不读取系统和用户的 git 配置；
  - 首次连接记下服务器的主机密钥，之后主机密钥变了就拒绝连接，防止冒充。

## 文件和目录

| 位置 | 属于 | 内容 |
| --- | --- | --- |
| `/opt/supervisord/deploy/任务名/spec.json` | root | root 批准过的任务内容，只有 root 能改；主机面板可以读它，认出由同步管理的目录 |
| `/opt/supervisord/deploy/任务名/work/` | 网站用户 | 部署私钥、主机密钥、同步缓存，只有网站用户能读 |
| `/opt/supervisord/deploy/任务名/state/` | 网站用户，supervisord 可读 | 状态文件、部署公钥 |
| `/opt/supervisord/data/deploy/任务名/` | supervisord，网站的组可读 | 控制台按钮发出的请求 |
| `/etc/systemd/system/go-supervisord-deploy@.service`、`.timer`、`.path` | root | 同步程序的 systemd 单元模板 |
| `/etc/systemd/system/go-supervisord-deploy@任务名.*.d/approved.conf` | root | 批准时写入：用户、组、可写目录、检查间隔 |

systemd 只从 `/etc/systemd/system` 加载单元，所以单元文件不在 `/opt` 下。

## 和原来的脚本对比

| | 原来的脚本 | 代码同步 |
| --- | --- | --- |
| 运行方式 | root 身份死循环，每 10 秒 `git pull` | 每 30 秒启动一次同步程序，跑完就退出 |
| 权限 | 全部 root 权限 | 网站用户身份，只能写这一个网站目录 |
| 账号密码 | 隔一阵要重新输入 | 部署公钥，不会过期 |
| 线上文件被改过 | 要合并，`git pull` 中断 | 按仓库覆盖 |
| 多出来的文件（例如被上传的木马） | 执行 `git clean` 时才删，嵌套的 Git 仓库删不掉 | 每次检查都删（白名单除外），控制台记录删了什么 |
| `.git` | 在网站目录里，一直变大 | 不在网站目录里，大小固定 |
| 失败 | 没人知道 | 控制台显示原因和记录 |
| 回滚 | 手动 `git reset` | 控制台选一个版本 |

## 限制

- **原地更新：** 更新的一两秒内，新旧文件可能同时存在，和原来的脚本一样。
- **依赖：** 服务器要装 `git` 和 `openssh-client`；配置了同步任务时，`install.sh` 会自动安装。
- **平台：** 只支持使用 systemd 的 Linux。
- **子模块：** 不拉取。
- **大文件：** 用 Git LFS 存的大文件不会下载。
